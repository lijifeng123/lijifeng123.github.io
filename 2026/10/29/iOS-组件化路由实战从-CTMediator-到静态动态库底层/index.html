iOS 组件化路由实战：从 CTMediator 到静态/动态库底层

发表于 2026-10-29

中型 iOS App 迭代到一定阶段，通常会遇到几个共性问题：所有页面靠 import 头文件硬耦合，改一个基础类会牵动整个工程；多团队并行开发时，谁都能改别人模块的内部代码，边界形同虚设；主工程全量编译动辄十几分钟，改个小按钮也要等上一轮构建；想做按需加载、给冷门业务瘦身，却一直无从下手。

组件化要解决的就是这类问题：把大 App 拆成相互独立的业务模块和基础模块，模块之间只通过约定的路由接口通信，从而实现单模块独立编译、独立测试、按需复用。

两种主流路由方案

1. URL 协议路由

启动时把页面路径和对应的页面创建 Block 注册到公共字典，调用时用 URL 匹配 Block、传入参数生成目标 VC。

优点在于直观易懂，H5 与 Native 可以统一跳转；代价是必须维护一份全局公共协议表，每新增页面都要同步更新，多人协作时容易出现协议命名冲突。

2. CTMediator 的 Target-Action 方案

靠隐式命名约定解耦。每个业务模块内部维护一个 Target_ 前缀的中转类，在其中实现对应的 Action 方法，返回页面或业务结果。调用方只传 target 与 action 字符串，运行期通过命名找到中转类并执行方法，同时自带类缺失的容错日志。

它不需要维护公共协议表，只需团队统一命名规范，是中小团队实施组件化的轻量选择。缺点是字符串无法在编译期校验，拼错要到运行期才暴露。

配套底层：静态库与动态库

  • 静态库：编译期把代码直接合并进主可执行文件，启动时一次性加载。适合网络、工具等基础通用模块和高频业务模块，与 CTMediator 配合最稳定，不存在运行时找不到类的问题。
  • 动态库：打包后以独立 .framework 形式存在，默认启动加载，也可配置为按需触发。适合冷门业务模块做主包瘦身。需要注意：用 CTMediator 调用前必须确保对应动态库已加载完成，否则会找不到 Target 中转类。

组件化实施要点

  • 基础能力层按能力抽成通用静态库。
  • 业务层按完整用户场景拆成独立模块。
  • 内部头文件与实现全部私有，只对外暴露上层封装的、以 mediator 前缀命名的分类 API。

核心成本在于命名规范与版本对齐——提前定好变更同步规则。长期来看，单模块独立编译与测试带来的收益，远高于维护成本。
