iOS WebView 封装实战：Hybrid 容器、JSBridge 与模块化交互设计

本文结合一个真实 iOS 项目的 WebView 封装，梳理 Hybrid 页面容器的整体设计，并重点拆解 Native 与 Web 的双向通信、第三方 WebViewJavascriptBridge 的底层原理，以及如何通过模块化避免容器类无限膨胀。

一、为什么不能只创建一个 WKWebView

在业务初期，打开一个 H5 页面可能只需要几行代码：创建 WKWebView、构造 NSURLRequest、调用 loadRequest:。

但随着 Hybrid 业务增多，问题会快速出现：

  • 每个页面都重复处理导航栏、进度条、Loading 和返回逻辑；
  • H5 需要调用分享、登录、相机、原生路由等 Native 能力；
  • Native 也需要向 H5 发送 App 前后台状态、页面关闭通知等消息；
  • 不同页面对标题、Cookie、Header、外链拦截的要求不同；
  • JS 调用方法越来越多，最终全部堆进一个庞大的 Controller；
  • Web 内容进程异常、页面加载失败和脚本消息处理器释放容易被忽略。

因此，一个可长期维护的 WebView 封装，不应该只是 WKWebView 的语法糖，而应该是一个完整的 Hybrid 页面容器：

统一入口和配置 + WebView 容器 + JSBridge 双向通信 + 模块化原生能力 + URL 路由拦截 + 生命周期管理。

  • 监控层：记录页面加载、失败和 Web 内容进程异常等事件。

三、容器层：统一初始化和页面配置

1. 统一 WebView 创建流程

容器在内部集中完成 WKWebViewConfiguration 和 WKWebView 的初始化，包括：

  • 追加自定义 UserAgent 和业务场景标识；
  • 配置内联播放、AirPlay 和自动播放策略；
  • 根据业务需要注入 WKUserScript；
  • 设置 WKNavigationDelegate 和 WKUIDelegate；
  • 监听网页标题和 estimatedProgress；
  • DEBUG 环境开启 Web Inspector 和资源加载调试。

业务方不再关心这些细节，只需要提供 URL 和配置。

2. 用配置对象承接页面差异

项目通过 UGWebUIConfig 控制不同页面的行为，常见配置包括：

  • 是否自动使用网页标题；
  • 是否显示进度条和中心 Loading；
  • 是否支持返回、分享和旋转；
  • 是否拦截外链；
  • 自定义 Cookie 和 HTTP Header；
  • 是否清除认证信息；
  • 首页 Tab 等特殊场景。

这种做法的核心价值是：用配置解决页面差异，而不是为每种业务创建一个 WebViewController 子类。

对于真正属于某个业务的特殊行为，则应该放进业务 Module，而不是继续给配置对象增加大量一次性开关。

方案 特点 项目中的主要用途
WebViewJavascriptBridge 自带 Handler 注册、消息队列和回调协议，但当前版本依赖自定义 Scheme 主要 Hybrid 业务通信
WKScriptMessageHandler WKWebView 原生消息通道，直接、清晰 触摸事件、调试消息等独立通知

如果重新设计一套轻量 Bridge，可以优先考虑 WKScriptMessageHandler + evaluateJavaScript，减少伪导航。但如果现有三方 Bridge 已稳定承载大量业务，就没有必要只为“更原生”而整体重写，关键是保持协议清晰和模块边界合理。

六、两套业务分发方式：Handler 与 Module

1. 旧版：按 handlerName 分发

这种方式简单直接，适合方法较少的阶段。但随着业务增长，if/else 和 Controller Category 会越来越多，公共能力与业务调用仍然集中在容器附近。

2. 新版：namespace + method 模块化

新版协议为消息增加命名空间：

UGHybridBridge 接收并反序列化消息后，将消息广播给已注册模块。每个 Module 自己判断：

  1. namespace 是否匹配；
  2. method 是否属于自己的支持集合；
  3. 是否需要经过拦截器；
  4. 如何执行并回调 H5。

例如 Navigation Module 只负责：

  • closePage：关闭当前原生容器；
  • popBack：WebView 能后退则后退，否则关闭容器；
  • openSysBrowser：打开系统浏览器。

这种设计的重点是：Bridge 只负责传消息，Module 才负责具体能力。

新增业务能力时，应该优先新增或扩展 Module，而不是继续修改容器。容器只负责注册模块和提供必要的宿主能力。

七、URL 跳转为什么要独立成路由策略

Hybrid 页面中的链接可能对应多种行为：

  • 普通 H5 页面，继续在当前 WebView 加载；
  • App 内部页面，转交 Native Router；
  • 自定义 Scheme，唤起其他 App；
  • 外部 HTTP/HTTPS 链接，选择 App 内或系统浏览器打开；
  • target="_blank"，决定是否在当前页面加载；
  • 特殊业务域名，进入定制流程。

项目在 decidePolicyForNavigationAction: 中集中处理这些分支，并将复杂的外链判断交给独立 Interceptor。

核心原则是：

Web 页面只表达“要去哪里”，Native 路由和拦截器决定“以什么方式打开”。

这样 H5 不需要理解 iOS 的 Controller 跳转细节，Native 也能统一实施安全限制、外链提示和特殊业务规则。

八、生命周期与资源释放不能漏

一个完整的 WebView 容器还需要处理以下问题：

  • 页面开始、完成和失败时更新 Loading 与进度条；
  • 通过 WKUIDelegate 将 JS Alert、Confirm、Prompt 转为原生弹窗；
  • App 进入后台或回到前台时通知 H5；
  • 监听 webViewWebContentProcessDidTerminate:，记录 Web 内容进程异常；
  • 页面销毁时清空 navigationDelegate 和 UIDelegate；
  • 页面消失或销毁时移除对应的 ScriptMessageHandler；
  • 清理通知、手势、延迟任务和不再需要的观察订阅。

尤其要注意：

WKUserContentController 对 ScriptMessageHandler 的持有关系如果处理不当，容易造成容器无法释放。动态注册和移除时，还要保证同一时期的添加与移除成对出现，避免重复注册或移除不存在的 Handler。

九、从这套封装中可以沉淀什么

这套实现最值得借鉴的，不是具体类名，而是以下边界：

  1. 容器只负责承载页面，不要把所有业务都写进 Controller；
  2. 配置负责通用差异，不要用大量子类复制 WebView 初始化代码；
  3. Bridge 只负责通信，序列化、回调和协议保持统一；
  4. Module 负责原生能力，通过命名空间和方法名隔离业务；
  5. Router 负责跳转策略，H5 不直接控制 Native 导航细节；
  6. 生命周期独立管理，加载失败、进程异常和资源释放都有明确处理；
  7. 理解三方库的底层实现，不能把所有 Bridge 都简单等同于 WKScriptMessageHandler。

十、总结

iOS WebView 封装的本质，是把一个单纯的内容渲染控件升级为可配置、可通信、可路由、可监控的 Hybrid 容器。
